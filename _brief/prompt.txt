PROMPT — BUILD "HASI DESIGNS", THE CINEMATIC PORTFOLIO OF HUSSNAIN SOHAIL

You are the creative director, motion designer, creative technologist and senior full-stack engineer for HASI DESIGNS, the personal portfolio of Hussnain Sohail. You will rebuild his portfolio from zero inside the GitHub repository HASI-desings/MY-PORTFOLIO (branch main). Treat every component as the most important part of the project. No throwaway work, no template look, nothing generic.

------------------------------------------------------------
WHAT I AM GIVING YOU
------------------------------------------------------------
Eight specification files and two assets. Put them all in a folder named _brief/ at the root of the repository (assets inside _brief/assets/) if they are not there already.

1. App.md        — THE VISION. What the site is, who it is for, the six scenes in summary, and WHY every major decision was made. Read it first. When you are unsure what to do, return to App.md section 4 ("Why it is built this way").

2. Design.md     — THE LOOK, THE LAYOUT AND THE MOTION. Exact colours, fonts, type scale, grid, the visibility hierarchy (what is shown immediately vs on scroll, hover, click or form), the exact position of every fixed element and button, every transition and animation with timings and easings, how each component reacts to hover/tap/focus/resize/tab-switch/reduced-motion, and the responsive rules for every screen size. This is the most detailed file; follow it precisely.

3. Structure.md  — THE CODEBASE. The exact folder/file tree, what each file is responsible for, how data flows from the content files to the scenes and the 3D canvas, and the content types. Build exactly this structure.

4. Phases.md     — THE ORDER OF WORK. Fifteen phases (0–14) with "Done when" criteria and approval stops marked with ⛔. Work strictly in this order and stop at every ⛔ for my approval.

5. Rules.md      — THE LAW. Everything you must and must never do: honesty about content, design limits, motion rules, code quality, performance, accessibility, responsiveness, git and delivery, and the Definition of Done. If any files disagree, Rules.md wins, then Design.md, then the others.

6. Security.md   — RESILIENCE. Security headers, link safety, and every situation that could break, stall or frustrate a visitor (slow loading, failed assets, offline, WebGL crashes, blocked links, missing mail app, error pages, no-JavaScript) with the exact solution for each.

7. reference.md  — REFERENCES AND RESOURCES. How to study the inspiration video, what to take from it and what to never take, and the exact names of every package, font, logo and URL.

8. prompt.txt    — this file: how to use the others.

ASSETS:

- _brief/assets/ME.png — my own silhouette portrait. It is the ONLY image of me. Remove its background (no other changes to it) and use it ONLY in Scene 06, the final scene.

------------------------------------------------------------
A scroll-controlled cinematic film in six scenes — 01 Identity (giant 3D HASI lettering, no person), 02 Toolkit (my real tools floating in 3D around an abstract Core), 03 What I Create (six disciplines, each with its own live code-built visual), 04 Selected Projects (real projects as liftable plates with honest LIVE / IN DEVELOPMENT / CONCEPT status), 05 Philosophy (pure giant typography: "CREATIVITY IS A PROCESS, NOT A TRAIT."), 06 Final (my silhouette is revealed for the first time; the red "LET'S MAKE IT REAL" button rises from the bottom and opens prefilled Email and WhatsApp). Palette: Obsidian #111217, Ice Grey #DFE5EB, Racing Red #EF233C used only as a signal. Everything is live code that reacts to scroll, hover and tap. It must work beautifully on every screen size, from small phones to ultrawide monitors, in portrait and landscape.

HOW TO WORK
------------------------------------------------------------
1. Read ALL eight files completely before doing anything. Then read App.md again.
2. Start with Phases.md Phase 0: delete every old file in MY-PORTFOLIO except .git/ and _brief/, commit, push.
3. Follow the phases in order. At the end of each phase: verify its "Done when" list, update docs/PROGRESS.md, commit and push.
4. Stop at every ⛔ approval stop and send me a short summary (with screenshots where the phase is visual). Continue only after I approve.
5. Explain what you build section by section (architecture, scroll timeline, 3D setup, loading pipeline) so I understand it — not line by line.
6. Report only tests that actually ran and passed. Never claim something works without checking it.
7. If something in the spec is ambiguous, choose what best serves App.md section 4, write the decision in docs/DECISIONS.md, and tell me at the next stop.
8. If anything I asked for would hurt performance, accessibility or honesty, tell me plainly and propose the better move.
9. Commit and push to GitHub only. DO NOT DEPLOY. I will deploy to Vercel myself.

------------------------------------------------------------
WHY THE FILES ARE SPLIT THIS WAY
------------------------------------------------------------
- App.md keeps you aligned with the purpose when details get complicated.
- Design.md removes guesswork: positions, timings and reactions are already decided, so the result is precise instead of generic.
- Structure.md keeps the code modular, so scenes, content and 3D stay separate and I can edit content or add projects later without touching animation code.
- Phases.md makes the build predictable and lets me review the look early (Scene 01 is the look test) before you build everything else.
- Rules.md protects honesty, quality and my identity (correct name spelling, no invented facts, no changes to my photo).
- Security.md makes sure no visitor ever sees a broken, frozen or confusing screen.
- reference.md keeps inspiration as inspiration, not copying, and removes any doubt about which resources to use.
